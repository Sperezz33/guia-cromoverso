Qué pasa cuando alguien abre la página

  1. El navegador pide cromoverso-sperezz33.vercel.app/mundos/neon a Vercel.
  2. En el servidor de Vercel, Next.js ejecuta layout.tsx: lee las cookies consentimiento e idioma, decide el idioma y pide los textos a GET /textos?idioma=es.
  3. Después ejecuta mundos/[id]/page.tsx: pide en paralelo el mundo, la lista de mundos y las rarezas. Si hay ?rareza= o ?tipo= en la URL, pide los cromos filtrados.
  4. Next.js arma el HTML completo y lo envía. La persona ve la página de una vez, ya en su idioma y sin parpadeo del aviso de cookies.
  5. En el navegador, React «hidrata» los componentes interactivos (menú móvil, selector de idioma, aviso de cookies, filtros en móvil) para que respondan a clics y teclado.
  6. Si cambia el idioma, una Server Action pide los textos nuevos, el contexto los reparte a todos los componentes y, si aceptó cookies, se guarda la cookie idioma.

React en el navegador es el mesero que sigue atendiendo después de servir: si pides otra cosa (cambiar de idioma), va a la cocina y vuelve sin que tengas que pararte de la mesa.

Parte 1 · Fundamentos de la web

1.1 Cliente, servidor y HTTP

Concepto

La web funciona con peticiones y respuestas. Un cliente (el navegador, o un programa) envía una petición a un servidor, y el servidor contesta con una respuesta. El idioma en que hablan se llama HTTP (HTTPS es la versión cifrada).

Una petición tiene:

  • Método: qué quieres hacer. GET = leer, POST = crear, PUT/PATCH = modificar, DELETE = borrar.
  • URL: a quién y qué. Por ejemplo https://yanethm-cromoverso-api.fly.dev/api/v1/cromos?rareza=dorada&tipo=heroe. Lo que va después de ? es la cadena de consulta (query string): pares clave=valor unidos con &.
  • Cabeceras (headers): datos extra. Ej.: Accept: application/json («respóndeme en JSON»), Cookie: idioma=en.
  • Cuerpo (body): datos que envías, solo en POST/PUT/PATCH.

Una respuesta tiene un código de estado, cabeceras y un cuerpo.

CódigoSignificaEjemplo en Cromoverso
200 OKTodo bienGET /mundos devuelve los 6 mundos
204 No ContentBien, pero sin cuerpo(Taquilla: DELETE /sesion)
400 Bad RequestPediste algo mal formadoGET /textos?idioma=fr → idioma_no_soportado
401 UnauthorizedNo has iniciado sesión(sprints siguientes)
404 Not FoundNo existeGET /mundos/no-existe → la página de no encontrado
422 UnprocessableEntendí, pero el dato no es válidoGET /cromos?rareza=inventada
5xxFalló el servidor503 simulado con X-Simular-Error

Regla fácil: 2xx éxito, 4xx el error es de quien pide (no vale la pena repetir igual), 5xx el error es del servidor (puede ser pasajero, vale la pena reintentar). Esta regla es justo la que usa el proyecto para decidir cuándo reintentar.

Analogía

HTTP es como pedir en una ventanilla. El método es el tipo de trámite, la URL es la ventanilla y el formulario, las cabeceras son las notas al margen («respóndame por escrito»), y el código de estado es el sello que te ponen: aprobado (200), no existe ese trámite (404), formulario mal lleno (422), o «el sistema se cayó, vuelva en un rato» (503).

JSON

JSON es el formato de texto en que la API envía los datos. Se parece a los objetos de JavaScript: llaves {} para objetos, corchetes [] para listas, y las claves siempre entre comillas dobles.

{
  "datos": [
    { "id": "neon", "nombre": "…", "numeros": { "desde": 1, "hasta": 20 }, "totalCromos": 20 }
  ]
}

Cookies

Una cookie es un dato pequeño (nombre=valor) que el navegador guarda para un sitio y envía automáticamente en cada petición a ese sitio. Por eso el servidor de Next.js puede saber el idioma elegido antes de armar la página. Cada cookie tiene opciones: cuánto dura (Max-Age), para qué rutas vale (Path), si solo viaja por HTTPS (Secure), si la puede leer JavaScript (HttpOnly la oculta) y cuándo se envía desde otros sitios (SameSite).

En Cromoverso

El servidor de Next.js (en Vercel) es cliente de la API: todas las peticiones a la API las hace el servidor, no el navegador. El navegador solo habla con Vercel. Esto tiene ventajas: la dirección de la API queda en una variable de entorno, se puede usar caché, y no hay problemas de CORS (permisos entre dominios distintos).

En Taquilla

Es exactamente igual: la API de Taquilla vive en https://yanethm-taquilla-api.fly.dev/api/v1, responde JSON y usa los mismos códigos. Su contrato también tiene 404 no_encontrado (un evento que no existe), 400 idioma_no_soportado y 422 validacion. Además tiene 401, 409 y 429, porque Taquilla ya tiene inicio de sesión y registro en su API.

1.2 HTML semántico

Concepto

HTML describe la estructura y el significado del contenido. «Semántico» quiere decir usar la etiqueta que dice qué es cada cosa, no solo cómo se ve. Un <div> no significa nada; un <nav> significa «esto es navegación». Los lectores de pantalla (programas que leen la página en voz alta a personas ciegas), los buscadores y el teclado usan ese significado.

<main>Contenido principal (uno por página)layout.tsx, con id="contenido"
<section>Sección temática con títuloPortada y mundos del inicio, aviso de cookies

Analogía

Un libro tiene portada, índice, capítulos y contraportada. Si todo fuera «hojas» sin títulos, nadie encontraría nada. Las etiquetas semánticas son esos títulos de capítulo: una persona ciega con lector de pantalla puede «saltar al índice» (nav) o «ir al capítulo» (main) igual que tú pasas páginas con el dedo.

Atributos que importan

  • lang en <html lang="es">: dice el idioma de la página para que el lector de pantalla pronuncie bien. El proyecto lo cambia a en cuando eliges inglés.
  • id: nombre único de un elemento. #contenido es el destino del enlace «Saltar al contenido».
  • alt en imágenes, aria-* para accesibilidad (ver la sección de accesibilidad), hidden para ocultar del todo.
En Cromoverso

El esqueleto que arma src/app/layout.tsx para todas las vistas:

<html lang={idioma}>

    <SaltarAlContenido />   {/* enlace oculto hasta recibir foco */}
    <GestorCookies />       {/* aviso, solo si no ha decidido */}
    <Encabezado />          {/* <header> con <nav> */}
    <main id="contenido" tabIndex={-1}>{children}</main>
    <Pie />                 {/* <footer> */}
  </body>

En Taquilla

El mismo esqueleto sirve: header con la navegación (Inicio, Explorar), main con la vista y footer. En el detalle de un evento, el título del evento sería el h1, y «Funciones» y «Localidades» serían h2. La lista de eventos en Explorar sería una <ul> de tarjetas.

1.3 CSS: cascada, variables y layout

Concepto

CSS define cómo se ve el HTML. Una regla tiene un selector (a qué elementos aplica) y declaraciones (propiedad: valor).

.boton { background: var(--marca-primario); padding: var(--espacio-3); }

«Cascada» significa que cuando varias reglas tocan el mismo elemento gana la más específica (un #id pesa más que una .clase, que pesa más que una etiqueta) y, si empatan, la que va de última.

Variables CSS (custom properties)

Una variable CSS se declara con dos guiones y se usa con var(). Si se declara en :root (la raíz del documento, o sea <html>), está disponible en toda la página.

:root { --marca-primario: #6c3bff; }
.boton { background: var(--marca-primario); }

También se pueden declarar en un elemento y solo valen ahí y en sus hijos. El componente Icono usa eso: le pone a cada icono su propia variable --icono con la URL del SVG.

Unidades y valores que verás

  • px píxeles; rem relativo al tamaño de letra raíz; % relativo al padre; vw/vh porcentaje de la ventana; fr fracción del espacio libre en una rejilla.
  • Atajos (shorthand): font: var(--tipo-cuerpo-m) pone de una vez el peso, el tamaño, el interlineado y la familia. El proyecto lo usa para no escribir tamaños de letra a mano.
  • currentColor: «el color del texto actual». Los iconos lo usan para tomar el color del texto que los rodea.

Flexbox y Grid

Flexbox ordena elementos en una dimensión (fila o columna). Ideal para barras: logo a la izquierda, enlaces al centro, botones a la derecha. 
.barra { display: flex;
  justify-content: space-between;
  align-items: center;
  gap: var(--espacio-4); }
Grid ordena en dos dimensiones (filas y columnas). Ideal para rejillas de tarjetas. 
.rejilla { display: grid;
  grid-template-columns:
    repeat(5, 1fr);
  gap: var(--espacio-4); }

Media queries (diseño adaptable)

Una media query aplica reglas solo si se cumple una condición, normalmente el ancho de la ventana:

.rejilla { grid-template-columns: repeat(5, 1fr); }      /* web */
@media (max-width: 1199px) { .rejilla { grid-template-columns: repeat(4, 1fr); } }
@media (max-width: 959px)  { .rejilla { grid-template-columns: repeat(3, 1fr); } }

Otras media queries del proyecto: prefers-reduced-motion (la persona pidió en su sistema menos animaciones) y los cortes de 767px y 959px para pasar al menú móvil y a los filtros en desplegables.

CSS Modules

Un archivo Boton.module.css es un CSS Module: sus clases se importan en el componente como un objeto, y Next.js les cambia el nombre por uno único (por ejemplo Boton_primario__x7a2b). Así dos componentes pueden tener una clase .primario sin pisarse.

import estilos from "./Boton.module.css";
<button className={estilos.primario}>Aceptar</button>
Analogía

Las variables CSS son como la paleta de pinturas de un pintor: en vez de mezclar el morado cada vez, lo tiene en un frasco con etiqueta «morado de marca». Si un día cambia el tono, cambia un frasco y todos los cuadros cambian. Los CSS Modules son como poner el nombre del dueño en cada frasco: dos pintores pueden tener un frasco «azul» sin confundirse.

En Cromoverso

Los estilos están en tres niveles:

  1. src/styles/tokens.css: todas las variables (colores, tipografía, espacios, radios, sombras). Es la única fuente de valores.
  2. src/app/globals.css: reglas generales (reset, tipo de letra del body, el anillo de foco :focus-visible, la clase .contenedor, .solo-lectores y la reducción de movimiento).
  3. Un .module.css por componente, que solo usa var(--...).

Otras técnicas de CSS en el proyecto: mask-image para los iconos, position: sticky para el encabezado, scroll-snap para el carrusel de mundos en móvil, conic-gradient y radial-gradient para el brillo holográfico de los cromos.

En Taquilla

Taquilla tendría su propio tokens.css exportado de su Figma, con sus colores y tipografías. Un detalle propio de Taquilla: el campo afiche de un evento no es una foto sino dos colores y un patrón ({ color1, color2, patron }). Se pinta con un degradado CSS, algo como background: linear-gradient(135deg, var(--c1), var(--c2)) donde --c1 y --c2 se pasan con style desde el componente, igual que Cromoverso pasa --icono o el color del cromo.

Operadores que salvan de errores

  • a?.b (encadenamiento opcional): si a es null o undefined, da undefined en vez de romper. Ej.: almacen.get("idioma")?.value.
  • a ?? b (fusión de nulos): usa b solo si a es null o undefined. Ej.: preferencias.idioma ?? idiomas?.predeterminado ?? "es".
  • cond ? x : y (ternario): un if/else en una expresión.

Asincronía: promesas, async/await y Promise.all

Concepto

Pedir datos por internet tarda. JavaScript no se queda congelado esperando: la petición devuelve una promesa, un objeto que dice «el resultado llegará después». Con await esperas a que se cumpla, dentro de una función marcada async. Si la promesa falla, await lanza un error que atrapas con try/catch.

Promise.all([a, b, c]) lanza varias promesas a la vez y espera a que terminen todas. Si una falla, falla todo.

// En serie: 3 esperas una tras otra (lento)
const mundo = await obtenerMundo(id);
const mundos = await obtenerMundos();
const rarezas = await obtenerRarezas();

// En paralelo: las 3 viajan juntas (lo que hace el proyecto)
const [mundo, mundos, rarezas] = await Promise.all([
  obtenerMundo(id), obtenerMundos(), obtenerRarezas(),
]);
Analogía

Una promesa es el ficho que te dan en una panadería: no tienes el pan todavía, pero tienes la garantía de que te lo entregarán (o te dirán que se acabó). Promise.all es mandar a tres amigos a tres panaderías al mismo tiempo en vez de ir tú a una, luego a otra y luego a otra.

fetch, clases y errores

const respuesta = await fetch(url, { headers: { Accept: "application/json" } });
if (!respuesta.ok) throw new ErrorApi(respuesta.status, "codigo", "mensaje");
const datos = await respuesta.json();

respuesta.ok es true si el código está entre 200 y 299. ErrorApi es una clase que hereda de Error (class ErrorApi extends Error) y le agrega el estado HTTP y el código de la API, para poder preguntar después error instanceof ErrorApi && error.estado === 404.

1.5 TypeScript

Concepto

TypeScript es JavaScript con tipos: le dices al editor qué forma tiene cada dato, y él te avisa antes de ejecutar si lo usas mal. Al compilar, los tipos desaparecen y queda JavaScript normal. Los archivos son .ts (lógica) y .tsx (con JSX, o sea componentes).

Analogía

Los tipos son como las formas de un juguete de encajar figuras: el círculo solo entra por el hueco redondo. Si intentas meter un texto donde va un número, TypeScript no te deja «encajarlo», y te das cuenta al escribir, no cuando el usuario ya está usando la página.

Lo que verás en el proyecto

Parte 2 · React

2.1 Componentes, JSX y props

Concepto

React es una librería para construir interfaces con componentes: funciones que reciben datos y devuelven lo que se debe ver. En vez de escribir una página gigante, la armas con piezas: Boton, TarjetaCromo, Encabezado…

JSX es la sintaxis parecida a HTML que va dentro de JavaScript. Diferencias con HTML: className en vez de class, htmlFor en vez de for, los valores de JavaScript van entre llaves { }, y los atributos se escriben en camelCase (tabIndex, onClick).

Props son los datos que un componente recibe del que lo usa, como los parámetros de una función. children es una prop especial: lo que va entre la etiqueta de apertura y la de cierre.

type Props = { variante?: "primario" | "secundario"; children: ReactNode; onClick?: () => void };

export function Boton({ variante = "primario", children, onClick }: Props) {
  return (
    <button className={estilos[variante]} onClick={onClick}>
      {children}
    </button>
  );
}

// Uso:
<Boton variante="secundario" onClick={() => decidir(false)}>Rechazar</Boton>

Listas y la prop key

Para pintar una lista se usa .map(). Cada elemento necesita una key única para que React sepa cuál es cuál si la lista cambia.

{mundos.map((mundo) => <TarjetaMundo key={mundo.id} mundo={mundo} />)}

Mostrar algo solo si se cumple una condición

{activo ? <Etiqueta>Estás aquí</Etiqueta> : <Icono nombre="chevronder" />}
{cromos.length === 0 && <EstadoVacio />}
if (consentimiento !== null) return null;   // no pinta nada
Analogía

Los componentes son fichas de Lego. Una ficha Boton se fabrica una vez y se usa en mil lugares; las props son el color y el tamaño que eliges para cada uso. children es lo que metes dentro de una ficha hueca.

En Cromoverso

Los componentes están en cuatro carpetas según su nivel:

  • components/ui: piezas base del sistema de diseño (Boton, BotonEnlace, Campo, Etiqueta, Tarjeta, Icono, SelectorIdioma, AvisoCookies). No piden textos a la API: los reciben por props. Así son reutilizables y fáciles de probar.
  • components/layout: lo que se repite en todas las vistas (Encabezado, MenuMovil, Pie, Marca, Idioma, SaltarAlContenido, GestorCookies).
  • components/catalogo: piezas del álbum (TarjetaCromo, TarjetaMundo, InsigniaRareza, IlustracionCromo, FiltrosMovil).
  • components/vistas: una vista completa armada con las piezas (VistaInicio, VistaCatalogo, VistaCuenta). Además components/estados/Estado para carga, vacío y error.

Ejemplo de separación: AvisoCookies (ui) solo dibuja el aviso con los textos que le pasen; GestorCookies (layout) decide si mostrarlo, saca los textos del contexto con t("cookies.banner.titulo") y ejecuta la decisión.

En Taquilla

La misma división funciona: ui igual (botón, campo, etiqueta, tarjeta, selector de idioma, aviso de cookies); y en vez de catalogo tendría algo como eventos con TarjetaEvento, Afiche (el degradado), InsigniaDisponibilidad (agotado / últimas entradas) y los filtros de categoría, ciudad, búsqueda y orden.

2.2 Estado y hooks

Concepto

El estado es la memoria de un componente: datos que cambian mientras la persona usa la página (¿el menú está abierto?, ¿qué idioma eligió?). Cuando el estado cambia, React vuelve a ejecutar el componente y actualiza solo lo que cambió en pantalla.

Los hooks son funciones que empiezan por use y le dan superpoderes a un componente. Reglas: se llaman siempre en el nivel superior del componente (no dentro de un if ni de un bucle) y solo en componentes de cliente.

useState es una pizarra que el componente mira cada vez que se dibuja: si alguien borra y escribe otra cosa, se vuelve a dibujar. useEffect es una nota que dice «cuando termines de dibujar, haz esto otro», como cerrar la puerta (bloquear el scroll) al abrir el menú; la función de limpieza es «y cuando te vayas, vuelve a abrirla». useRef es un dedo que señala un elemento de la página para poder tocarlo después.

Por qué useCallback arregló un error real

En el menú móvil, un useEffect enfoca el primer enlace cuando el menú se abre, y depende de la función onCerrar. Sin useCallback, el Encabezado creaba una función cerrarMenu nueva en cada render; el efecto veía «cambió onCerrar» y volvía a enfocar el primer enlace una y otra vez, así que el foco saltaba solo. Con useCallback(..., []) la función es la misma siempre y el efecto solo corre al abrir.

Cerrar el menú al cambiar de ruta sin useEffect

En Encabezado.tsx se guarda la ruta anterior en estado y, si es distinta a la actual, se cierra el menú durante el render. Es el patrón que recomienda React para «ajustar estado cuando cambia una prop», y evita la regla de ESLint react-hooks/set-state-in-effect (no llamar setState directamente dentro de un efecto).

const [rutaAnterior, setRutaAnterior] = useState(rutaActual);
if (rutaActual !== rutaAnterior) {
  setRutaAnterior(rutaActual);
  setAbierto(false);
}
En Taquilla

Los mismos hooks: useState para el menú y para el campo de búsqueda; useTransition o un estado de carga al cambiar de idioma; useEffect para el foco del menú y el lang. En los formularios de ingreso y registro (sprints siguientes) aparecería useActionState o un estado de «enviando» para deshabilitar el botón mientras responde la API.

2.3 Context: datos para toda la app

Concepto

Normalmente los datos bajan de padre a hijo por props. Si un dato lo necesitan muchos componentes en distintos niveles (el idioma, los textos), pasarlo por props en cada nivel es tedioso («prop drilling»). Analogía

Sin contexto, es como pasar un mensaje de mano en mano por toda una fila de personas. Con contexto, es como la emisora de radio del edificio: el Provider transmite, y cualquiera que encienda su radio (usePreferencias()) escucha lo mismo, sin importar en qué piso esté.

3.1 Qué es Next.js y el App Router

Concepto

React solo dibuja componentes. Next.js es un framework encima de React que agrega lo que falta para una web completa: rutas por carpetas, ejecución en el servidor, caché, optimización de fuentes e imágenes, y la compilación para producción.

El App Router es la forma de organizar rutas en la carpeta src/app: cada carpeta es un segmento de la URL y el archivo page.tsx dentro de ella es lo que se ve en esa URL.

Analogía

La carpeta app es el directorio de un edificio. Cada carpeta es un piso u oficina, y page.tsx es la puerta de esa oficina. layout.tsx es el pasillo común (con el letrero del edificio y la salida) que se ve desde todas las oficinas.

mundos/page.tsx/mundos → redirige al primer mundo
mundos/[id]/page.tsx/mundos/neon, /mundos/cualquier-cosa (ruta dinámica)
ingresar/page.tsx, registro/page.tsx/ingresar, /registro

global-error.tsxError que tumba hasta el layout

globals.cssNo es ruta: estilos globales

  • params y searchParams son promesas: se escribe const { id } = await params;.
  • cookies() es asíncrona: const almacen = await cookies();.
  • error.tsx recibe una función retry para reintentar (en versiones anteriores se llamaba reset).
  • Tipos globales generados: PageProps<"/mundos/[id]"> y LayoutProps<"/"> (por eso existe next typegen en el script de tipos).

3.2 Rutas dinámicas, params y searchParams

Concepto

Una carpeta con corchetes, como [id], es un segmento dinámico: atrapa cualquier valor en esa posición de la URL. Next.js le entrega a la página ese valor en params. Lo que va después de ? en la URL llega en searchParams.

URL /mundos/neon?rareza=legendaria&tipo=heroe → params = { id: "neon" } y searchParams = { rareza: "legendaria", tipo: "heroe" }.

Analogía

[id] es un casillero con nombre variable: «Oficina del mundo ___». La recepcionista lee el nombre en la puerta (params.id) y busca el expediente. Los searchParams son las notas adhesivas pegadas en la solicitud: «solo legendarias, solo héroes».

En Cromoverso 
export default async function CatalogoDeMundo({ params, searchParams }: PageProps<"/mundos/[id]">) {
  const { id } = await params;
  const [mundo, mundos, rarezas] = await Promise.all([
    mundoONoEncontrado(id), obtenerMundos(), obtenerRarezas(),
  ]);
  const filtros = leerFiltros(await searchParams, rarezas.datos);
  const hayFiltros = Boolean(filtros.rareza || filtros.tipo);
  // Sin filtros bastan los 20 cromos de GET /mundos/:id; con filtros se piden a GET /cromos.
  const cromos = hayFiltros
    ? (await obtenerCromos({ mundo: mundo.id, ...filtros, porPagina: 20 })).datos
    : mundo.cromos;
  return <VistaCatalogo mundo={mundo} mundos={mundos.datos} rarezas={rarezas.datos} cromos={cromos} filtros={filtros} />;
}

Otras herramientas de navegación de Next.js en el proyecto:

  • notFound(): corta la página y muestra not-found.tsx. Se llama si la API responde 404 para ese mundo.
  • redirect(url): manda a otra ruta. /mundos redirige al primer mundo que entrega la API.
  • <Link href>: enlace que navega sin recargar toda la página.
  • router.push(url, { scroll: false }): navegar por código (los selects de filtros en móvil).
En Taquilla

app/eventos/[slug]/page.tsx recibe params.slug y llama GET /eventos/:slug; si la API responde 404 no_encontrado, el contrato dice textualmente que se use notFound(). Explorar lee de searchParams los filtros categoria, ciudad, q, orden y pagina, y se los pasa a GET /eventos.

3.3 Server Components y Client Components

Concepto

En el App Router, todos los componentes son de servidor por defecto. Un Server Component se ejecuta solo en el servidor: puede ser async, hacer await fetch(...), leer cookies y variables de entorno secretas. Su código no se envía al navegador; solo viaja el resultado (HTML).

Un Client Component empieza con la línea "use client". Se pinta primero en el servidor (para que el HTML llegue completo) y luego se «hidrata» en el navegador: ahí puede usar estado, efectos, eventos (onClick), document y window.

Server ComponentClient Component
MarcaNinguna (por defecto)"use client" en la primera línea
Puede pedir datos con awaitSíNo directamente
Hooks (useState, useEffect)NoSí
Eventos (onClick)NoSí
Ve process.env.API_URLSíNo (solo variables NEXT_PUBLIC_)
Envía JavaScript al navegadorNoSí
Analogía

Un Server Component es como un plato que llega ya cocinado a la mesa: no necesitas la receta ni los ingredientes, solo el resultado. Un Client Component es como una parrilla de mesa: llega cocinada, pero trae su fuego para que tú sigas interactuando (voltear la carne = abrir el menú).

En Cromoverso
  • Servidor: layout.tsx, todas las page.tsx, lib/api.ts, lib/preferencias-servidor.ts, lib/seo.ts. Ahí se piden los datos.
  • Cliente: el contexto Preferencias.tsx, Encabezado, MenuMovil, Idioma, GestorCookies, SaltarAlContenido, FiltrosMovil, las vistas (porque usan t() del contexto), loading.tsx y not-found.tsx (usan t()), y error.tsx y global-error.tsx (Next.js exige que sean de cliente).

El patrón: la página (servidor) pide los datos y se los pasa como props a la vista (cliente). La vista no hace peticiones; solo dibuja y reacciona.

Ojo

Lo que pasa del servidor al cliente por props tiene que poder convertirse a texto (serializable): objetos, listas, textos, números. No se pueden pasar funciones normales ni clases. Por eso el contexto recibe textos (un objeto) y no la función obtenerTextos.

En Taquilla

Mismo patrón. Algo extra que Taquilla necesitará en los sprints de sesión: el contrato recomienda que el ingreso se haga en una Server Action y que el token se guarde en una cookie httpOnly del frontend, enviándolo desde el servidor como Authorization: Bearer <token>. Eso solo es posible en código de servidor. Nunca en localStorage.

3.4 loading, error, not-found y global-error

Concepto

Next.js tiene archivos con nombre especial que muestran estados sin que tengas que programar la lógica:

  • loading.tsx: se muestra al instante mientras la página espera sus datos (Next.js usa streaming: envía primero el marco y el estado de carga, y luego el contenido cuando llega).
  • error.tsx: si la página lanza un error, en vez de romperse todo se muestra este componente, con una función para reintentar. Es un límite de error (error boundary): el error no sube más allá.
  • not-found.tsx: lo que se ve cuando se llama notFound() o la ruta no existe.
  • global-error.tsx: el último recurso, cuando falla el propio layout.tsx. Como reemplaza al layout, debe tener su propio <html> y <body>.
Analogía

loading es el letrero «estamos preparando su pedido». error es el mesero que dice «se nos quemó, ¿lo preparo otra vez?». not-found es «ese plato no está en la carta». global-error es cuando se va la luz en todo el restaurante: ni siquiera hay carta, así que alguien sale con una linterna y un aviso escrito a mano.

En Cromoverso

Los tres primeros usan el componente Estado y textos de la API (estados.cargando, estados.error, estados.noEncontrado). error.tsx:

"use client";
export default function ErrorDeVista({ error, retry }: { error: unknown; retry: () => void }) {
  const { t } = usePreferencias();
  useEffect(() => { console.error(error); }, [error]);
  return (
    <Estado icono="alerta" nivel="h1" rol="alert"
      titulo={t("estados.error.titulo")} texto={t("estados.error.texto")}>
      <Boton variante="primario" icono="intercambio" onClick={() => retry()}>
        {t("estados.error.botones.reintentar")}
      </Boton>
    </Estado>
  );
}

global-error.tsx es especial: si el layout falló, probablemente GET /textos no respondió, así que no hay textos. Intenta cargarlos con la Server Action (con el idioma de la cookie); si tampoco puede, usa un respaldo bilingüe escrito en el código: «No se pudo cargar · Could not load», «La API no responde. Vuelve a intentarlo en unos segundos.» y «Reintentar · Try again». Es la única excepción a la regla de no escribir textos en el código, y está justificada porque sin API no hay de dónde sacarlos.

Pregunta trampa

«¿Por qué /mundos/no-existe responde 200 y no 404?» Porque existe loading.tsx: Next.js empieza a enviar la respuesta (con el estado de carga) antes de saber que el mundo no existe, y el código de estado HTTP ya salió como 200. La persona sí ve la página de no encontrado, y Next.js agrega <meta name="robots" content="noindex"> para que los buscadores no la indexen. Es un comportamiento conocido del streaming.

En Taquilla

Su contrato pide lo mismo: estado de carga mientras la petición está en curso, estado de error con botón de reintentar para 500 error_interno y falla_simulada, la página de no encontrado para un slug inexistente, y un estado vacío cuando GET /eventos responde datos: [] (por ejemplo ?q=zzzz). Ojo: sin resultados no es un error, es 200 con lista vacía.

3.5 Server Actions

Concepto

Una Server Action es una función async que vive en el servidor pero se puede llamar desde un componente de cliente como si fuera local. Se marca con "use server". Next.js crea por debajo una petición HTTP (POST) desde el navegador al servidor, ejecuta la función allá y devuelve el resultado.

Analogía

Es el timbre de la cocina. El mesero (cliente) no entra a cocinar; toca el timbre con la orden («textos en inglés»), la cocina (servidor) prepara y le devuelve el plato.

En Cromoverso

src/app/acciones.ts tiene una sola acción:

"use server";
export async function cargarTextos(idioma: IdIdioma): Promise<Textos> {
  if (!esIdioma(idioma)) throw new Error("idioma_no_soportado");
  const respuesta = await obtenerTextos(idioma);
  return respuesta.textos;
}

¿Por qué no hacer fetch a la API directo desde el navegador? (1) La dirección de la API está en API_URL, que solo existe en el servidor. (2) Se reutiliza la misma función con caché y reintentos. (3) Se valida el idioma en el servidor: aunque alguien llame la acción con "fr" a mano, se rechaza antes de ir a la API.

En Taquilla

Mismo uso para el cambio de idioma. En sprints siguientes, Taquilla las usaría mucho más: ingresar (POST /sesion), registrarse (POST /usuarios), verificar el correo, recuperar la clave. Ahí la acción recibe los datos del formulario, llama a la API y devuelve los errores de campos para mostrarlos junto a cada campo.

3.6 Caché de fetch y revalidate

Concepto

Una caché es una copia guardada de una respuesta para no pedirla otra vez. En Next.js, un fetch con next: { revalidate: N } guarda la respuesta y la reutiliza durante N segundos. Pasado ese tiempo, la próxima visita recibe todavía la copia vieja (rápido) mientras Next.js pide una nueva por detrás. Si esa nueva petición falla, se sigue sirviendo la copia anterior.

Analogía

Es el menú del día escrito en el tablero. No le preguntas al chef cada vez que entra un cliente; cada 5 minutos alguien revisa si cambió. Si el chef no contesta, el tablero sigue mostrando el menú anterior en vez de quedar en blanco.

En Cromoverso
DatosConstanteSegundosPor qué
/idiomas, /textosCACHE_TEXTOS300 (5 min)Los textos casi nunca cambian
/mundos, /mundos/:id, /rarezas, /cromosCACHE_CATALOGO60 (1 min)Datos del catálogo, pueden cambiar más

Beneficios concretos: la API de Fly.io se apaga si nadie la usa y tarda en despertar; la caché hace que la mayoría de visitas no esperen ese arranque, y que una caída corta de la API no tumbe el sitio. También reduce la carga sobre una API que comparte todo el curso.

En Taquilla

Lo mismo para textos, categorías, ciudades y eventos. Pero nada que dependa de la sesión puede ir en caché compartida: GET /sesion debe pedirse sin caché (cache: "no-store"), porque si no, una persona podría ver el nombre de otra.

Concepto

Parte 4 · La API

4.1 REST, JSON y el contrato

Concepto

Una API (interfaz de programación) es una puerta para que un programa le pida datos a otro. Una API REST organiza esos datos como recursos con URLs (/mundos, /mundos/neon, /cromos) y usa los métodos HTTP para decir qué hacer con ellos. Un endpoint es una combinación método + ruta, por ejemplo GET /mundos/:id (los dos puntos marcan una parte variable).

El contrato es el documento que dice qué endpoints hay, qué reciben, qué responden y qué errores pueden dar. Es el acuerdo entre quien hace la API (la profesora) y quien la usa (tú). Además existe la especificación OpenAPI (/docs/openapi.yaml), que es el mismo contrato en un formato que leen las máquinas, y la página /docs para probar los endpoints en el navegador.

Analogía

El contrato es la carta del restaurante: dice qué platos hay, qué traen y cuánto cuestan. No puedes pedir algo que no está en la carta (un filtro inventado da 422), y si lo pides bien, sabes exactamente qué te llega.

En Cromoverso

Endpoints que usa el Sprint 1 (base https://yanethm-cromoverso-api.fly.dev/api/v1):

EndpointQué devuelveLo usa
GET /idiomas{ predeterminado: "es", datos: [{ codigo, nombre }] }Layout (selector ES | EN)
GET /textos?idioma=es{ idioma, version, textos: {...} }, todos los textos de la interfazLayout, Server Action, metadatos
GET /mundos{ datos: [6 mundos], totalAlbum }Inicio, catálogo (panel Mundos), redirección de /mundos
GET /mundos/:idEl mundo con sus cromos (20) y sus especialesCatálogo

Detalles del contrato que se respetaron:

4.2 El cliente de la API (src/lib/api.ts)

Concepto

Un cliente de API es un archivo que concentra todas las llamadas a la API. Las páginas no escriben fetch ni URLs: llaman funciones con nombre claro (obtenerMundo(id)). Si mañana cambia la dirección, el formato de error o la caché, se cambia en un solo lugar.

Analogía

En Cromoverso, pieza por pieza 
// 1. Un error con la forma del contrato
export class ErrorApi extends Error {
  constructor(readonly estado: number, readonly codigo: string, mensaje: string) {
    super(mensaje);
    this.name = "ErrorApi";
  }
}

// 2. La dirección sale de la variable de entorno, sin "/" al final
function direccionBase() {
  const base = process.env.API_URL;
  if (!base) throw new Error("Falta la variable de entorno API_URL (revisa .env.example).");
  return base.replace(/\/+$/, "");
}

// 3. Una petición: cabeceras, caché y conversión del error
async function pedirUnaVez<T>(ruta: string, segundosEnCache: number): Promise<T> {
  const respuesta = await fetch(`${direccionBase()}${ruta}`, {
    headers: { Accept: "application/json", ...cabecerasDePrueba() },
    next: { revalidate: segundosEnCache },
  });
  if (!respuesta.ok) {
    const cuerpo = await respuesta.json().catch(() => null);
    throw new ErrorApi(respuesta.status,
      cuerpo?.error?.codigo ?? "error_interno",
      cuerpo?.error?.mensaje ?? `HTTP ${respuesta.status}`);
  }
  return (await respuesta.json()) as T;
}

// 4. Funciones públicas, una por endpoint
export function obtenerMundo(id: string) {
  return pedir<MundoConCromos>(`/mundos/${encodeURIComponent(id)}`, CACHE_CATALOGO);
}
export function obtenerCromos(filtros: FiltrosCromos) {
  const parametros = new URLSearchParams({ edicion: "album" });
  for (const [clave, valor] of Object.entries(filtros)) {
    if (valor !== undefined && valor !== "") parametros.set(clave, String(valor));
  }
  return pedir<ListaPaginada<Cromo>>(`/cromos?${parametros}`, CACHE_CATALOGO);
}
  • <T> (genérico): cada función dice qué tipo de respuesta espera, y TypeScript lo sabe en la página.
  • encodeURIComponent(id): escapa caracteres raros para que un id con espacios o / no rompa la URL.
  • URLSearchParams: arma edicion=album&mundo=neon&rareza=legendaria correctamente codificado y omite los filtros vacíos.
  • .catch(() => null) al leer el cuerpo del error: si el servidor no respondió JSON (por ejemplo una página HTML de error), no se rompe.

4.4 Reintentos y simulación de fallas

Concepto

Resiliencia es que la aplicación aguante fallas sin caerse. Una técnica es reintentar las peticiones que fallan por causas pasajeras, esperando un poco más cada vez (backoff). Lo importante es reintentar solo lo que tiene sentido: un 5xx o un corte de red pueden ser momentáneos; un 404 o un 422 no van a cambiar por repetir.

Analogía

Si llamas a alguien y da ocupado, esperas un momento y vuelves a llamar, y si vuelve a dar ocupado, esperas un poco más. Pero si te dicen «ese número no existe», no tiene sentido seguir marcando.

En Cromoverso 
const ESPERAS_REINTENTO = [300, 900];   // ms antes del 1.er y 2.º reintento

function valeLaPenaReintentar(error: unknown) {
  return !(error instanceof ErrorApi) || error.estado >= 500;   // red caída o 5xx
}

async function pedir<T>(ruta: string, segundosEnCache: number): Promise<T> {
  for (let intento = 0; ; intento++) {
    try {
      return await pedirUnaVez<T>(ruta, segundosEnCache);
    } catch (error) {
      const espera = ESPERAS_REINTENTO[intento];
      if (espera === undefined || !valeLaPenaReintentar(error)) throw error;
      await new Promise((listo) => setTimeout(listo, espera));
    }
  }
}

En total: hasta 3 intentos (1 + 2 reintentos), con esperas de 0,3 s y 0,9 s. Si todo falla, el error sube y lo atrapa error.tsx (o global-error.tsx si falló el layout).

Otras protecciones (PR #10):

  • obtenerIdiomasSiHay(): si GET /idiomas falla, devuelve null y el selector se arma con textos.idioma.opciones (idiomasDesdeTextos). El idioma por defecto queda en IDIOMA_DE_RESPALDO = "es".
  • metadatosDePagina devuelve {} si falla: la página se ve sin título personalizado, pero se ve.
  • cromosDestacados() del inicio devuelve [] si falla: la portada sale sin cartas destacadas.
  • global-error.tsx con respaldo bilingüe y botón de reintentar.

Cómo simular fallas para la demo

La API acepta dos cabeceras de prueba. El proyecto las envía solo si existen las variables en .env.local:

5.5 US-CRO-S1-05 · Cambiar el idioma entre español e inglés

Concepto: internacionalización (i18n)

i18n (i + 18 letras + n) es preparar una aplicación para varios idiomas. La regla del curso: ningún texto va escrito en los componentes; todos vienen de GET /textos?idioma=es|en como un objeto anidado, y cada componente pide el suyo por su ruta ("navbar.enlaces.inicio").

Dos detalles: los marcadores ("Ver {mundo}" se rellena con el nombre) y los plurales ({ uno: "1 cromo", otro: "{cantidad} cromos" }).

Analogía

Es como un teatro con subtítulos: la obra (los componentes) es la misma; lo que cambia es el rollo de subtítulos que se proyecta. Cambiar de idioma es cambiar de rollo, no reescribir la obra.

En Cromoverso

El flujo completo

  1. Primera carga (servidor): layout.tsx decide el idioma así: preferencias.idioma ?? idiomas?.predeterminado ?? "es" (la cookie, si aceptó cookies; si no, el predeterminado de la API; si no, español). Pide los textos y pone <html lang={idioma}>.
  2. Clic en EN: Idioma.tsx llama cambiarIdioma("en") del contexto.
  3. useTransition marca cambiandoIdioma = true: el contenedor del selector lleva aria-busy y no se aceptan más clics hasta que termine.
  4. La Server Action cargarTextos("en") trae los textos en inglés.
  5. El contexto actualiza textos e idioma: todos los componentes que usan t() se vuelven a pintar en inglés, sin recargar la página.
  6. Un useEffect pone document.documentElement.lang = "en" y useTituloDePagina cambia el título de la pestaña.
  7. Si la persona aceptó cookies, se guarda la cookie idioma=en. Al volver mañana, el servidor la lee y la página llega directamente en inglés.

Leerlas en el servidor (sin parpadeo)

export async function leerPreferencias() {
  const almacen = await cookies();
  const consentimiento = almacen.get("consentimiento")?.value;
  const idioma = almacen.get("idioma")?.value;
  const valido = esConsentimiento(consentimiento) ? consentimiento : null;
  return {
    consentimiento: valido,
    idioma: valido === "aceptado" && esIdioma(idioma) ? idioma : null,   // sin consentimiento, el idioma no cuenta
  };
}

  • Al decidir, el aviso desaparece y el foco pasa a #contenido, para que quien navega con teclado no quede «en el aire».

7.1 Git y GitHub: conceptos

Concepto
  • Git: programa de control de versiones. Guarda la historia del proyecto como una serie de fotos llamadas commits.
  • Repositorio: la carpeta del proyecto más su historia (la carpeta oculta .git).
  • Commit: una foto de los cambios, con un mensaje, autor, fecha y un identificador (hash, como c530b5a).
  • Staging (área de preparación): dónde eliges qué cambios entran en el próximo commit (git add).
  • Rama (branch): una línea de trabajo paralela. main es la principal; cada historia se hizo en su rama.
  • Merge (fusionar): unir los commits de una rama en otra.
  • Remoto: la copia del repositorio en otro lugar (GitHub), llamada origin. push sube, pull baja y fusiona, fetch solo baja.
  • GitHub: sitio que aloja repositorios y agrega herramientas de equipo, como los pull requests (PR): una solicitud para fusionar una rama en otra, con su descripción, revisión y comentarios.
Analogía

Git es como guardar partida en un videojuego: cada commit es un punto de guardado al que puedes volver. Una rama es jugar una partida alternativa sin arruinar la principal. Un merge es traer lo que lograste en la alterna a la principal. Un PR es pedirle al grupo «miren lo que hice en mi partida alterna, ¿lo traemos a la principal?».

7.2 Cómo se trabajó con ramas y PR en Cromoverso

  1. Una rama por historia, cada una creada a partir de la anterior (ramas encadenadas), porque cada historia necesitaba el código de la anterior: S1-02 usa los componentes de S1-01, etc.
  2. Un PR por historia: #3 (S1-01) hacia main; #4 (S1-02) hacia la rama de S1-01; #5 hacia la de S1-02; y así hasta #8.
  3. Al fusionar, las ramas no se borraron. Por eso GitHub no cambió la base de los PR siguientes a main, y los PR #4 a #8 se fusionaron cada uno en su rama base, no en main. Resultado: main solo tenía S1-01.
  4. Se detectó revisando la historia de main, y se creó el PR #9 de integración desde feat/s1-03-inicio hacia main: después de fusionar el #8 en ella, esa rama ya contenía todas las historias. No trajo cambios nuevos, solo integró lo ya revisado.
  5. Luego #10 (fix/resiliencia-api), #11 y #12 (documentación), ya directamente hacia main.
Esto es lo que va en IA.md como «respuesta equivocada»

Claude Code afirmó que al fusionar el primer PR, GitHub cambiaría la base de los siguientes a main automáticamente. Eso solo pasa si se borra la rama base al fusionar. La lección: antes de fusionar, revisar a qué rama apunta el PR («base: main ← compare: feat/...»).

Protección de la rama y revisores

En GitHub se puede agregar a la profesora como colaboradora del repositorio (Settings → Collaborators). Agregarla no obliga a pedir su aprobación para fusionar; eso solo pasa si se configura una regla de protección de rama que exija revisiones.

8.3 Preguntas de sustentación

Intenta responder en voz alta antes de abrir la respuesta.

Arquitectura

¿Por qué Next.js y no React solo (o Vite, como el repo de referencia)?

Porque el curso pedía Next.js con App Router y TypeScript. Además da lo que el sprint necesita: pedir datos en el servidor, leer cookies antes de pintar (sin parpadeo), rutas por carpetas, estados de carga, error y 404 con archivos especiales, metadatos y despliegue directo en Vercel.

¿Qué diferencia hay entre un Server Component y un Client Component? Da un ejemplo de cada uno en el proyecto.

El de servidor se ejecuta solo en el servidor, puede hacer await a la API y no envía su código al navegador: mundos/[id]/page.tsx. El de cliente lleva "use client", se hidrata en el navegador y puede usar estado y eventos: MenuMovil.tsx.

¿Por qué las peticiones a la API las hace el servidor y no el navegador?

La dirección está en API_URL, que solo existe en el servidor; se aprovecha la caché de Next.js para todos los visitantes; el HTML llega completo (mejor para buscadores y para la primera carga); y no hay problemas de CORS.

¿Qué es Promise.all y por qué se usa?

Lanza varias promesas al tiempo y espera a que terminen todas. En el catálogo, mundo, mundos y rarezas viajan en paralelo: el tiempo total es el de la más lenta y no la suma de las tres.

¿Qué hace revalidate: 60?

Guarda la respuesta del fetch en caché y la reutiliza 60 segundos. Después, la siguiente visita recibe la copia guardada mientras se pide una nueva por detrás; si la nueva falla, se sigue usando la anterior. Los textos usan 300 s.

Datos y API

¿Qué pasa si escribo /mundos/neon?rareza=inventada?

leerFiltros compara el valor con las rarezas de GET /rarezas; como no existe, lo ignora y se muestran todos los cromos. Sin esa validación la API respondería 422 y se vería el estado de error.

¿Y si escribo /mundos/no-existe?

GET /mundos/no-existe responde 404; mundoONoEncontrado lo detecta (ErrorApi con estado 404) y llama notFound(), que muestra not-found.tsx. El código HTTP sale 200 por el streaming de loading.tsx, pero la página es la de no encontrado y lleva noindex.

¿Por qué los filtros van en la URL y no en useState?

Para que sobrevivan a una recarga, se puedan compartir por enlace, funcione el botón «Atrás» y el servidor pinte la página ya filtrada.

¿Por qué edicion=album en todas las peticiones de cromos?

Porque la API también tiene cromos especiales, y el catálogo del álbum solo muestra los de la edición álbum (lo indica el contrato).

¿Qué pasa si la API está caída?

Cada petición se reintenta dos veces (0,3 s y 0,9 s) si el error es 5xx o de red. Si sigue fallando: si la página tenía datos en caché, se sirven; si no, en una vista se muestra error.tsx con «Reintentar»; si falla el layout (textos), se muestra global-error.tsx con un respaldo bilingüe. Si solo falla /idiomas, el selector se arma con los textos.

¿Por qué no se reintenta un 404?

Porque es un error de quien pide: el recurso no existe y no va a aparecer por repetir. Reintentar solo haría la respuesta más lenta.

¿Cómo muestras el estado de carga y de error en la demo?

En .env.local pongo API_SIMULAR_LATENCIA=2000 o API_SIMULAR_ERROR=503 y reinicio npm run dev. El cliente de la API los envía como las cabeceras X-Simular-Latencia y X-Simular-Error.

Idioma y cookies

¿Dónde están los textos de la interfaz? ¿Hay alguno escrito en el código?

Todos vienen de GET /textos. La única excepción es el respaldo de global-error.tsx, porque se muestra justo cuando la API no responde y no hay de dónde sacar textos.

Explica paso a paso qué pasa al hacer clic en «EN».

cambiarIdioma("en") → useTransition marca la carga → la Server Action cargarTextos("en") pide los textos → el contexto cambia textos e idioma → todos los t() se repintan → un efecto cambia <html lang> y otro el título → si aceptó cookies, se guarda idioma=en.

¿Por qué las cookies se leen en el servidor?

Para que el HTML llegue ya correcto: en el idioma recordado y sin el aviso si ya decidió. Si se leyeran en el navegador, se vería el aviso o el idioma equivocado por un instante (parpadeo).

Si rechazo las cookies, ¿por qué sí se guarda la cookie consentimiento?

Porque es necesaria para recordar la propia decisión; si no, el aviso aparecería en cada página. Lo que no se guarda es la preferencia (idioma), y si existía, se borra.

¿Qué significan Max-Age, SameSite=Lax y Secure?

Max-Age: cuántos segundos dura (180 días). SameSite=Lax: no se envía en peticiones de otros sitios salvo al navegar con un enlace, lo que protege de ataques entre sitios. Secure: solo viaja por HTTPS (se agrega cuando el sitio está en HTTPS).

¿Por qué «Aceptar» y «Rechazar» se ven iguales si en Figma no?

El segundo criterio de S1-06 pide que ninguna opción tenga más peso. Por eso las dos usan la variante secundaria y el mismo ancho. Está documentado como decisión propia en IA.md.

¿Cómo funcionan los plurales?

Algunos textos vienen como { uno, otro }. traducir elige uno si valores.cantidad === 1 y otro en los demás casos, y luego rellena los marcadores como {cantidad}.

Diseño y accesibilidad

¿Qué es un token de diseño? Muéstrame uno.

Una decisión de diseño guardada como variable: --marca-primario: #6c3bff o --tipo-cuerpo-m: 400 16px / 24px var(--fuente-rubik) en tokens.css. Los componentes usan var(--...) en vez de valores escritos a mano.

¿Cómo toman color los iconos?

El SVG se usa como máscara de un span cuyo fondo es currentColor. Así el icono toma el color del texto que lo rodea y se puede cambiar con CSS.

¿Cómo se usa el menú móvil solo con teclado?

Tab hasta el botón, Enter abre y enfoca el primer enlace. Tab da la vuelta dentro del menú y el botón. Escape cierra y devuelve el foco al botón. El botón anuncia su estado con aria-expanded.

¿Para qué sirve aria-current? ¿Y aria-pressed?

aria-current="page" anuncia el enlace de la página actual (o "true" para el filtro activo). aria-pressed anuncia si un botón conmutable está activo (ES/EN).

¿Por qué la rareza muestra icono y palabra y no solo color?

Para no depender del color: una persona con daltonismo o un lector de pantalla no distinguirían «épica» de «rara» solo por el color.

¿Qué pasa con las animaciones si la persona pidió reducir el movimiento?

Hay una media query prefers-reduced-motion: reduce en globals.css que las quita o reduce.
